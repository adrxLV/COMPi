# First coding-test preparation — evidence-based exam blueprint

This is a **practice blueprint from the supplied preparation test**, not a claim that the actual first coding test will reproduce its groups, questions, difficulty, scoring or length. The cover identifies it as “Preparation Test · Version I”; the course guide identifies coding test 1 as a paper test in week 7 (Saturday 24 October 2026), while the week-7 lecture labels the weeks 1–7 material as on Saturday's test. [`example_mini_test.pdf`, p. 1; `Computation_I_Course_Guide.pdf`, pp. 14, 22; `Computation_I_Lecture_07_slides.pdf`, p. 22]

## What the example actually contains

| Section | Count, response type and skill | Evidence |
|---|---|---|
| **Group 1 — read and predict** | **3 multiple-choice questions.** Predict exact output or evaluate a Boolean expression, including input strings versus integers, conversion/repetition, method chains, list append, loop tracing and formatting. Choose one offered answer, including the error/none options if applicable. | [`example_mini_test.pdf`, pp. 2–3] |
| **Group 2 — find and fix** | **2 code blocks.** State the issue briefly, then rewrite **only each faulty line** beneath it; leave other answer lines blank. Tasks combine range bounds, case-normalisation, string replacement/reassignment and f-string formatting, then `split`, `append`, whitespace, method calls, membership and valid last-index access. The instructions and worked example are on p. 4; questions on pp. 5–6. | [`example_mini_test.pdf`, pp. 4–6] |
| **Group 3 — complete fragments** | **1 direct question with five placeholders `<A>`–`<E>`.** Fill expressions/statements to split a semicolon-delimited string and names, create a lowercase bounded-length username, check for a duplicate and append to a list. | [`example_mini_test.pdf`, p. 7] |
| **Group 4 — open coding** | **One continuing scenario with 3 numbered parts:** (1) parse comma-separated student numbers, assign a room from parallel range lists, increment corresponding counts, handle no match; (2) print room counts and the busiest room; (3) parse corresponding names and determine an arrival time with ordered conditional exceptions. Parts build on the given initial lists and earlier answers. Prompts occur on pp. 8, 10 and 11; pp. 9 and 12 are answer space, p. 13 is extra space. | [`example_mini_test.pdf`, pp. 8–13] |

**Duration and marks:** the example says **1 hour 30 minutes**. Each group header says “X points total, Y points each question”; these are literal placeholders, not published numbers. The cover says question scores vary by group. Therefore neither point totals nor group percentages, passing cutoff for this particular test, or a prescribed time allocation per group can be recovered from this paper. [`example_mini_test.pdf`, pp. 1–2, 4, 7–8]

## A faithful rehearsal design

1. Rehearse **all four response modes on paper** within the example's 90-minute limit: output/Boolean traces; brief diagnosis plus corrected lines; five-place code completion; and one multi-part program that carries state forward. These are observed exercise formats, not a prediction of the live paper. [`example_mini_test.pdf`, pp. 1–12]
2. Trace types and state explicitly: `input()` is text; list mutation differs from a method returning `None`; string methods yield new strings; `range` stops before its bound; sequence indexing starts at zero; output formatting and branch order matter. These failure points occur in the sample and align with the first-half lectures. [`example_mini_test.pdf`, pp. 2–7, 11; `Computation_I_Lecture_02_slides.pdf`, pp. 24–28; `Computation_I_Lecture_04_slides.pdf`, pp. 8–12, 25–35; `Computation_I_Lecture_06_slides.pdf`, pp. 20–21]
3. Practise integrated weeks 1–7 programs using `split`/`strip`, conversion, `for`/`range`, `if`/`elif`/`else`, and list indexing/mutation. The week-7 lecture itself gives four corresponding review modes: write, fix, complete and predict. [`example_mini_test.pdf`, pp. 5–8, 10–11; `Computation_I_Lecture_07_slides.pdf`, pp. 23–26]
4. Treat `while`/`break`, nested loops, comprehensions, matrices and user-defined functions as **later-course topics**, not required first-test study targets on current evidence. The practical book contains later chapters, but the dated syllabus and week-7 test map supersede a chapter's mere presence. [`Computation_I_Course_Guide.pdf`, pp. 22–23; `Computation_I_Lecture_07_slides.pdf`, p. 22; `Computation_I_Practical_Exercises_Book_2026.pdf`, PDF pp. 2–3 (contents)]

## Rules and uncertainties

- **Confirmed for the example:** write on the supplied pages; legibility and a single selected answer matter; no books/notes/computers/phones, no student communication, and devices are excluded as described on its cover. **Confirmed generally by the course guide:** coding tests are on paper; no notes/books/documentation; only non-graphical calculators are permitted; phones and smart devices are to be switched off and left at the room entrance. Follow the actual proctor's instructions if the live test differs. [`example_mini_test.pdf`, p. 1; `Computation_I_Course_Guide.pdf`, pp. 14–15]
- **Assessment distinction:** the *average of two coding tests* contributes 30% of the course grade; the final exam contributes 70% and covers the **whole** program. It would be incorrect to say this 90-minute preparation mini-test is the final exam or to assign the 70% course weight to coding test 1. Moodle quizzes contribute 0%. [`Computation_I_Course_Guide.pdf`, p. 14]
- **Unconfirmed:** the official first-test duration, live group count/order, number of questions, marks per question, marking rubric, allowed calculator use on that particular sitting beyond the general rule, and whether every sample task type recurs. The sample alone establishes its **own** 90-minute duration and format, not those properties of the live test. [`example_mini_test.pdf`, pp. 1–8; `Computation_I_Course_Guide.pdf`, pp. 14–15]
